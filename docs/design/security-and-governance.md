# 安全、治理面与本地/云端划分（设计提案）

状态：提案，未锁定，**尚不完整**。日期：2026-11-14。

一次换模型的独立评审指出了 10 个高优先级问题，多数还没有解决方案，列在第 7 节。在这些问题解决之前，本文档不能作为实现依据，也不能作为对客户的安全承诺。完整设计在 MVP 之后做。

这份文档回答创始人在敲定 `architecture.md` 的 D-1 到 D-7 时交给设计的四件事：安全机制怎么做（D-3）、治理面管什么（D-4、D-5）、扩展怎么放行（D-2）、本地内容哪些不上云（D-6），以及 OpenClaw 怎么 fork（D-2）。每节末尾列出需要创始人拍板的点。

## 1. 安全机制（D-3）

### 1.1 一句话

agent 能做的事 = 用户本人的权限 ∩ 这个 agent 被授予的权限 ∩ 组织策略。三者取交集，默认拒绝。所有动作只有一个出口，在出口处判断、记录。

### 1.2 四类身份

| 身份 | 例子 | 凭据 |
|---|---|---|
| 用户 | 员工、管理员 | 企业 SSO 登录 |
| agent | 平台提供的、用户自建的 | 每次运行签发的短时令牌，写明用户、agent、版本、风险等级 |
| 节点 | 云端工作区、某台电脑上的本地执行器 | 设备注册时签发，可吊销 |
| 扩展 | 插件、技能 | 发布者签名 + 内容哈希 |

agent 永远拿不到用户的长期凭据（邮箱令牌、API key）。凭据存在凭据代理里，工具调用通过网关时由代理注入，模型上下文里不出现。

### 1.3 唯一出口：工具网关

工具调用、网络请求、文件读写、模型调用，全部经过运行时里的工具网关。网关对每个动作做四步：

1. **识别**：谁（用户、agent、版本、节点）、做什么（工具、目标资源）、涉及什么级别的数据。
2. **判断**：查策略，得出放行、拒绝或需要审批。
3. **执行**：放行则注入凭据并执行；需要审批则挂起等人。
4. **记录**：写一条审计事件（`packages/protocol` 的格式）。

这个设计有两个已知的洞（第 7 节 H1、H6），目前没有解决：

- 网关在运行时进程里。**在用户自己的电脑上，这个进程可以被用户或恶意软件改掉**，策略和审计都可以被绕过。本机节点应当视为不可信，A3、A4 的连接器动作和凭据应当只在服务端执行。
- 网关只看得到 agent 发起的工具调用，看不到 agent 在沙箱里运行的代码自己发的网络请求。必须再有一层 agent 代码够不着的边界（操作系统级沙箱配置、独立进程的出站代理）。

### 1.4 动作分级

策略不是逐个工具写规则，而是先把动作分级，再按级别定默认行为。

| 级别 | 含义 | 例子 | 默认 |
|---|---|---|---|
| A0 | 只读，不出工作区 | 读已授权的文件、搜索知识库 | 放行 |
| A1 | 在工作区或沙箱内写 | 生成文档、在沙箱里跑代码 | 放行 |
| A2 | 对外有影响但可撤回 | 建草稿、建日程、写入网盘 | 放行并记录，组织可改为审批 |
| A3 | 对外且难撤回 | 发邮件、发消息、删除、对外发布 | 用户本人确认 |
| A4 | 涉及钱、权限、批量数据导出 | 付款、改权限、导出客户名单 | 用户确认 + 管理员策略明确允许 |

每个工具在注册时声明自己的级别；没声明的按 A3 处理。浏览器自动化、沙箱里跑代码、通用 HTTP 这类通用工具能做到的事远超它声明的级别，按工具名分级对它们不成立，需要按实际效果和去向在调用时分级（第 7 节 H6）。管理员可以按部门、按 agent、按数据级别调严，不能把 A4 调成默认放行。

### 1.5 防提示注入

来自网页、邮件、文件、工具返回的内容都标记为「外部内容」，它不能作为指令。具体两条硬规则：

- 一次运行只要读过外部内容，之后的 A3、A4 动作一律需要用户确认，即使策略原本对该 agent 免确认。
- 读过「机密」及以上数据的运行，向组织外发送任何内容都需要确认，并在确认界面写明发给谁、带了什么。

这两条靠运行时的状态标记实现，不靠模型自觉。

评审认为这两条规则既太窄又太吵（第 7 节 H3）：A2 以下的动作同样能外泄数据（写进对外共享的文件夹、带外部参会人的日程、输出里的远程图片地址），标记不随存储和子 agent 传递；同时几乎每次读邮件的运行都会弹确认，用户会习惯性点同意。确认界面必须由网关根据实际调用生成，不能用模型写的摘要。这一节需要重做。

### 1.6 沙箱

- 代码执行只在沙箱里。
- 网络默认拒绝，出站走白名单代理。
- 文件只能访问被授权的目录。
- 每个会话一个隔离环境，会话之间不共享文件系统。

### 1.7 不拖性能的做法

| 环节 | 做法 | 目标 |
|---|---|---|
| 策略判断 | 策略由治理面签名下发，在运行时进程内判断，不逐次联网 | 每次判断 p99 低于 1 毫秒 |
| 审计写入 | 先写本地追加日志，再批量上传；动作不等上传完成 | 对动作延迟无可感知影响 |
| 审批 | 只有 A3、A4 和 1.5 的两种情况需要人确认 | A0 到 A2 零等待 |
| 技能扫描 | 在安装时做，不在运行时做 | 运行时零开销 |
| 凭据注入 | 代理缓存短时令牌 | 不为每次调用做一次登录 |

这些数字是设计目标，还没有实测。工具网关做出来后要有基准测试守住它们。

策略下发有延迟：管理员收紧策略后，运行时最长在一个刷新周期内仍按旧策略执行。建议刷新周期 60 秒，吊销 agent 和吊销节点走即时推送。

### 1.8 审计

每个动作一条事件，记录谁、做了什么、依据哪条策略、结果。参数只存摘要，不存内容。事件按租户成链。哈希链本身防不住能写日志的人，需要可信检查点（CHA-161）才算防篡改。

### 需要创始人拍板

- A2（建草稿、建日程这类）默认放行还是默认确认。建议放行，否则日常办公会被确认框打断，违背 D-1 的降低门槛。
- 策略刷新周期 60 秒是否可接受。

## 2. 扩展的放行（D-2）

### 2.1 两条通道

| | 插件 | 技能 |
|---|---|---|
| 是什么 | 代码，能注册工具、接入外部系统 | 指令和脚本，教 agent 做某类事 |
| 谁能引入 | 只有管理员或运营 | 用户可以自己装（组织可关闭） |
| 放行条件 | 人工审批通过，签名，进入组织目录 | 强制安全扫描通过，且不在黑名单 |
| 用户看到 | 目录里已批准的 | 自己装的 + 组织推荐的 |

### 2.2 技能的强制扫描

用户安装技能时，运行时不直接加载，先交给扫描器。扫描器是平台内置的、用户关不掉也改不了的一个技能，它做三件事：

1. **静态检查**：脚本里的危险调用、外联地址、读取凭据的路径、混淆代码。
2. **意图检查**：用模型读技能的指令，找「忽略之前的规则」「把内容发到某地址」这类注入和外泄意图。
3. **权限核对**：技能声明要用哪些工具、访问哪些域名，与实际内容是否一致。

结果三档：通过、需注意（列出发现，用户确认后可装，管理员可见）、拒绝。扫描结果按内容哈希缓存，内容一变就重扫。

扫描器会漏报。它是一道门槛，不是保证。

评审指出的问题（第 7 节 H4）：让模型读不可信的技能文本，技能可以直接对扫描器做提示注入；扫描器若跑在用户电脑上可以被改；技能可以写「去某地址取最新指令再执行」，静态扫描通过后运行时换内容。因此扫描应当只在服务端做、结果签名、运行时拒绝未签名的技能，「运行时再取远程指令」直接判拒绝，规则更新后要全量重扫。

### 2.3 权限清单

每个插件和技能带一份清单，写明它需要的工具、网络域名、数据级别。运行时按清单约束它，扩展的权限不会超过装它的用户。

限制：清单只能约束技能里的脚本。技能的指令是放进 agent 上下文的文字，加载之后 agent 的工具调用无法归到某个技能头上，所以「清单里没有的会被拒绝」对指令不成立（第 7 节 H5）。要么技能激活时把整次运行收窄到 agent 权限与技能清单的交集，要么明说只约束脚本。未定。

### 2.4 黑白名单

- **黑名单**：按内容哈希、发布者、名称。命中即禁用，已安装的立即停用。黑名单走即时推送。
- **白名单**：组织可以切到「只允许白名单」模式，此时用户只能装目录里的技能。
- 平台维护一份全局黑名单，各组织可以追加自己的。

### 需要创始人拍板

- 默认是否允许用户自己装技能。建议默认允许（扫描通过才行），由各组织决定是否收紧到白名单模式。
- 「需注意」档是让用户自己确认就能装，还是必须管理员批准。建议用户确认即可，但 A3 以上能力的技能必须管理员批准。

## 3. 治理面的范围（D-4、D-5）

### 3.1 模块

| 模块 | 管什么 |
|---|---|
| 组织与成员 | SSO、部门、角色、成员的权限分配 |
| Agent 花名册 | 每个 agent 的 UUID、负责人、版本、风险等级、状态、谁在用 |
| 运行与审计 | 每次运行的完整链路、审计日志查询与导出 |
| 策略与审批 | 动作分级的默认值、各部门的调整、待审批事项 |
| 扩展目录 | 插件审批、技能扫描结果、黑白名单 |
| 模型 | 接入哪些模型、密钥、按数据级别的路由、各模型价格 |
| 用量与计费 | 按用户、部门、agent、模型的用量和花费，预算和上限 |
| 连接器 | 邮箱、日历、网盘等外部系统的接入和授权范围 |
| 节点 | 云端工作区和已注册的本地设备，可吊销 |
| 健康 | 服务状态、失败率、告警 |

### 3.2 管理角色

| 角色 | 能做 |
|---|---|
| 所有者 | 全部，包括计费和删除组织 |
| 管理员 | 成员、agent、策略、扩展、模型、连接器 |
| 安全审计员 | 只读全部审计和策略，不能改 |
| 财务 | 只看用量和计费 |
| 成员 | 用 agent、建自己的 agent、装技能（在策略允许内） |

审计员和管理员分开，是为了管理员的操作也有人能查。管理员在后台的每个操作同样写审计事件。

### 3.3 agent 的身份与生命周期

- **来源**：平台提供、组织发布、用户自建。三种都有 UUID，都进花名册。
- **版本**：模型、指令、技能、工具任一变化就是新版本（`agentFingerprint`），审计记录指向具体版本。
- **状态**：草稿 → 已发布 → 已停用 → 已退役。停用即时生效。
- **负责人**：每个 agent 必须挂一个真人。负责人离职时 agent 自动停用，等待转交。

### 3.4 agent 的风险等级

等级由 agent 能做的最高级别动作和它是否无人值守决定，自动算出，不靠人填。

| 等级 | 条件 | 发布要求 |
|---|---|---|
| R1 | 只有 A0、A1 | 用户自建即可用 |
| R2 | 含 A2 | 用户自建即可用，进花名册 |
| R3 | 含 A3 | 分享给他人前需管理员批准 |
| R4 | 含 A4，或无人值守运行（定时、事件触发）且含 A3 | 必须管理员批准才能运行 |

agent 的定义一变，等级重算；升到更高等级时回到待批准状态。

### 3.5 使用记录

按 agent 记录：谁用过、每次运行的时间和结果、调用了哪些工具、被拒绝和被审批的次数、花费。这些应当从审计事件和用量事件聚合出来，不另存一份。但现在的 `packages/protocol` 做不到：事件里没有动作级别、风险等级、节点、审批过程、扩展身份、用量字段，也表达不了管理员操作（第 7 节 H7）。在做工具网关之前必须先扩展事件结构。

### 需要创始人拍板

- 计费是只做内部成本分摊（各部门花了多少），还是要对外向客户收费。两者数据相同，但后者要接支付和开票，范围大很多。建议第一版只做用量和内部分摊。
- 用户自建的 R1、R2 agent 是否需要管理员批准。建议不需要，否则违背降低门槛。

## 4. 本地与云端（D-6）

### 4.1 两种运行位置

这一节与 D-6 的「各端历史一致」有冲突：本机会话的内容默认不同步，换设备就看不到。D-6 的原话同时要求了两件事，这里的取舍需要创始人确认，确认后要么改这里的默认值，要么给 D-6 补一句例外。

每个会话在创建时选定运行位置，之后不变：

| | 云端工作区 | 本机 |
|---|---|---|
| agent 在哪跑 | 云端沙箱 | 用户电脑上的本地执行器 |
| 能碰什么 | 上传或同步进来的文件、连接器 | 用户授权的本地文件夹、本机命令 |
| 关电脑后 | 继续跑 | 停 |
| 手机上 | 完整可用 | 电脑在线时可查看和操控 |

这和 Codex、Claude Code 的做法一致：云端任务在云端沙箱跑，本地任务在本机跑，各有各的数据边界。

### 4.2 什么数据在哪

| 数据 | 云端会话 | 本机会话 |
|---|---|---|
| 身份、策略、agent 定义 | 云 | 云（本机缓存） |
| 审计事件（只有摘要，没有内容） | 云 | 云 |
| 用量 | 云 | 云 |
| 对话记录 | 云，各端同步 | 默认存本机；组织可允许用户选择同步 |
| 文件内容 | 用户放进工作区的才在云 | 不上传 |
| 命令输出、工具返回 | 云 | 存本机 |

要点：

- **审计不依赖内容上云。** 事件里只有摘要，不含内容。但有三点要说清：来自本机节点的审计是设备自己报的，设备被改就不可信，不能等同于云端审计；摘要是不带密钥的 SHA-256，参数可猜时（收件人地址、金额）别人能验证猜测，应改为带租户密钥的 HMAC；只有摘要回答不了「发给了谁」，需要另存不含内容的结构化信息（收件域名、文件 ID、大小）。
- **上传从不是副作用。** 本地文件只有在用户明确把它加进云端工作区时才上传。
- **模型调用走哪里还没定，而它决定了本地数据的实际去向。** 模型密钥在治理面，则本机会话的提示词要经过 Muster 的云，「云端不存」必须靠一个不记录内容的模型代理来保证；本机直连模型厂商，则密钥要放在设备上、用量靠设备自报。倾向前者加私有模型选项。
- **本机会话的内容仍会发给模型。** agent 读了一个本地文件，文件内容就会进入发给模型的请求。「不上云」指的是 Muster 的云端不存，不是内容不离开电脑。需要内容完全不出内网的组织，得接私有部署的模型。这一点必须对客户说清楚。

### 4.3 组织可设的规则

- 标为「受限」的数据只能在本机会话里处理。
- 或者反过来：禁止本机执行，一切在云端沙箱里跑。
- 本机会话的对话记录是否允许同步到云。

### 4.4 手机看本机会话

电脑在线时，手机通过中继连到电脑上的会话。中继只转发、不落盘，且手机与电脑之间必须端到端加密，否则中继能看到明文。电脑离线则看不到本机会话的内容，只能看到它存在和最后状态。

### 需要创始人拍板

- 本机会话的对话记录默认不同步。这意味着换一台设备看不到历史，与「全部打通」有张力。建议默认不同步、允许用户按会话开启，由组织策略兜底。
- 第一版先做哪个：云端工作区，还是本机。建议先云端（零安装、手机可用、对标 Muse 的常驻体验），本机第二步。

## 5. OpenClaw 的 fork 方式（D-2）

### 5.1 现状

本机一份 OpenClaw 2026.9.8 的规模（非测试的 TypeScript、Swift、Kotlin 行数，粗略统计）：

| 目录 | 行数 | 内容 |
|---|---|---|
| `src/` | 约 227 万 | 网关、agent、会话、插件、渠道、媒体、语音、向导等 |
| `extensions/` | 约 105 万 | 174 个扩展：各家模型、各种聊天渠道、搜索、语音 |
| `apps/` | 约 59 万 | macOS、iOS、Android、Linux 客户端 |
| `ui/` | 约 42 万 | 控制界面 |
| `packages/` | 约 11 万 | 25 个包：agent 核心、模型运行时、网关协议、插件 SDK、网络策略等 |

总量约 440 万行。「fork 之后往下删」不现实：删不干净，也没人能审完剩下的。

### 5.2 做法：按白名单搬入，不是按黑名单删除

1. 把上游固定在一个版本，作为只读参考放在仓库外（或 git 子模块），不参与构建。
2. Muster 的运行时从空目录开始，一次搬入一块需要的东西，每搬一块：记录来源路径和上游版本、审它的默认权限、把它接到工具网关上、补测试。
3. 一份清单（`runtime/UPSTREAM.md`）列出每块代码来自上游哪里、改了什么，上游出安全修复时知道要不要跟。

### 5.3 第一批候选

评审实际查了上游各包的依赖，结论如下（本机 OpenClaw 2026.9.8）：

| 包 | 结论 |
|---|---|
| `agent-core`（约 8 千行） | 适合第一个搬。非测试代码不依赖 `src/`；`agent-loop.ts` 已有工具调用前后的钩子，可以接网关。测试依赖 `src/`，要重写 |
| `ai`（约 3.4 万行） | 模型调用在这里。只搬一两家模型。模型调用不经过上面的钩子，网关要在这一层再包一次 |
| `llm-core`、`normalization-core`、`net-policy`、`retry`、`tool-call-repair` | 自成一体，便宜，可搬 |
| `plugin-sdk` | **不是独立的包**：几乎全是对 `src/plugin-sdk/` 的转出，那里约 5.8 万行并大量依赖 `src/` 其他部分。不搬，Muster 自己设计插件契约 |
| `gateway-protocol`（约 2.4 万行） | 是 OpenClaw 自己的控制协议，与 Muster 的治理面和 `packages/protocol` 冲突。不搬 |

建议的限时摸底范围：`agent-core` + `ai`（一两家模型）+ `llm-core` + `normalization-core` + `net-policy`，约 4.5 万行。`src/` 里的会话、技能加载、定时任务等，每块搬之前先同样量一遍依赖。

### 5.4 明确不搬

- 面向个人的聊天渠道（WhatsApp、Telegram、Discord、iMessage 等）
- 上游的各端客户端和控制界面（Muster 自己做，走 OpenUI）
- 语音、音乐、视频生成等与办公无关的能力
- 上游默认放开的本机命令执行路径（改为必须过网关和沙箱）

### 5.5 风险

- **耦合因包而异。** `agent-core` 干净，`plugin-sdk` 深度耦合。`src/` 有 227 万行，每一块都要先量依赖再决定。
- **上游变化快。** 版本固定后，跟进上游是有成本的手工活。
- **许可。** 上游是 MIT，可以 fork 和商用，需保留版权声明。

### 需要创始人拍板

- 是否同意「白名单搬入」而不是「整体 fork 再瘦身」。两者最终形态接近，前者每一步都可审、可测，后者前期快但长期留着审不完的代码。
- 是否先做一次限时摸底再定运行时 EPIC 的范围。

## 6. 建议的 EPIC 顺序

1. **运行时摸底**（限时）：从 OpenClaw 搬入最小核心，跑通一次带工具调用的对话。产出是「要搬多少」的事实，决定后面的范围。
2. **工具网关与策略**：动作分级、策略判断、审计写入、审批挂起。此后所有能力都建在它上面。
3. **治理面后端 + 管理后台第一版**：组织与成员、Agent 花名册、运行与审计、策略与审批。
4. **云端工作区 + 网页端**（OpenUI）：第一个可用的端到端产品。
5. **扩展目录**：插件审批、技能扫描、黑白名单。
6. **模型管理、用量与计费**。
7. **桌面端与本机会话**，然后**手机端**。
8. **可信检查点**（CHA-161）：在对外承诺「审计防篡改」之前必须完成。

第 2 步不依赖第 1 步的结果，可以并行。

## 7. 独立评审发现的问题（未解决）

评审由另一个模型（Claude Opus）只读完成，对照了 `architecture.md` 和 `packages/protocol` 的实际代码。下面是结论和现状。标「已改」的只是把文档里说过头的话改掉了，机制本身大多还没有设计。

### 高优先级

| 编号 | 问题 | 现状 |
|---|---|---|
| H1 | 网关只在云端是唯一出口；本机上可被用户或恶意软件绕过，沙箱里的代码也不经过它 | 已在 1.3 写明，无方案 |
| H2 | 插件是代码，凭据代理把令牌注入它构造的请求时，插件就能看到令牌并外发 | 无方案。方向：插件单独进程，只拿能力句柄；持有凭据的服务自己发请求 |
| H3 | 外部内容标记规则太窄（A2 以下可外泄、标记不随存储和子 agent 传递）又太吵（确认疲劳）；确认界面不能用模型写的摘要 | 已在 1.5 写明，需重做 |
| H4 | 扫描器可被它扫描的内容攻击；本机可篡改；技能可在运行时取远程指令 | 已在 2.2 写明方向，未设计 |
| H5 | 权限清单约束不了只有指令的技能 | 已在 2.3 写明，未定 |
| H6 | 通用工具（浏览器、沙箱代码、通用 HTTP、运行时列工具的 MCP）使动作分级和 agent 风险等级失真；插件作者自己声明级别 | 已在 1.4 写明，无方案 |
| H7 | `packages/protocol` 的事件记录不了设计假设的内容：动作级别、风险等级、策略版本、节点、标记状态、审批过程、去向、扩展身份、管理员操作、用量 | 已在 3.5 写明。做网关前必须先扩展 |
| H8 | 每租户一个连续序号的哈希链，与「本机先写再批量上传」不相容；A3、A4 可能在没有持久记录的情况下完成 | 无方案。方向：每节点一条用节点密钥签名的链，接入时锚定到租户链；A3、A4 前同步写入意图事件 |
| H9 | 对恶意管理员没有约束（接入自控模型端点导走数据、放宽策略、批准低报级别的插件）；平台运营能向所有租户推插件 | 无方案。方向：高危操作双人审批、实时通知审计员、管理员默认看不到对话内容、平台插件需租户同意、审计存储不受管理员控制 |
| H10 | 离线的本机节点收不到吊销，会一直按缓存策略运行；旧的宽松策略签名仍然有效，可以重放 | 无方案。方向：策略带有效期，过期降到只允许 A0、A1；版本只增不减 |

### 中优先级

- **审计摘要**：不带密钥的摘要可被猜测验证，且回答不了「发给了谁」。已在 4.2 写明。
- **模型调用路径未定**，决定本地数据去向。已在 4.2 写明。
- **「受限数据只能本机处理」没有办法知道哪些数据是受限的**：本地文件没有分级标签。未设计。
- **手机中继需要端到端加密**。已在 4.4 写明。
- **本机命令的说法前后矛盾**：1.6 说代码只在沙箱跑，4.1 说本机会话能跑本机命令，Windows 沙箱方案未知。另需固定禁区（`~/.ssh`、钥匙串、浏览器配置、云 CLI 凭据）和符号链接逃逸防护。未解决。
- **agent 版本指纹只含工具名，不含工具代码**：插件更新实现而名字不变时，指纹不变、风险等级不重算。需把插件和工具的内容哈希、连接器范围、模型路由纳入指纹。
- **共享 agent 和无人值守 agent 用谁的权限**没有说。方向：共享 agent 用调用者的权限；无人值守用单独的服务身份；排队的确认要有过期。
- **与 `architecture.md` 的冲突**：本机会话历史默认不同步与 D-6 冲突（已在第 4 节写明）；确认规则增加等待而无估算，与 D-3 冲突；沙箱内脚本和本机节点的行为不可审计，与 D-4 冲突；草稿状态的 agent 能否运行未说明，涉及 D-5。
- **「需注意」档由用户自己确认就能装**，容易被社工。评审建议收紧为：用户确认只适用于 A0、A1，其余需管理员批准。

### 低优先级

- 性能表缺了真正占时间的环节：沙箱冷启动、出站代理的 TLS、凭据服务往返。
- 「每次判断低于 1 毫秒」只对基于标签的进程内判断成立；一旦要检查内容或策略引擎在进程外，就不成立。
- 黑名单和吊销除了推送，还应在每次运行开始时检查。
- 没有频率和总量限制：大量低级别动作加起来等于一次批量导出。
- 离职处理只说了 agent 负责人，还应包括吊销令牌和节点、处理离职者设备上的本机数据、转交共享 agent 和定时任务。

### 企业客户的安全团队会问、而本文完全没有的

租户隔离（云端沙箱是否共享内核、数据存储隔离、每租户密钥）、密钥管理（凭据库、客户自带密钥、签名密钥轮换）、数据驻留与私有部署、模型厂商的数据处理（不训练、留存期限、各数据级别允许的厂商）、留存与删除、平台方人员对租户数据的访问、事件响应（各级熔断、取证导出、对接 SIEM）、用户贴进对话的密钥如何处理。

### 评审认为站得住的

三者取交集且默认拒绝；未声明的工具按 A3、A4 不能调成默认放行；风险等级自动计算、升级时重新审批；审计员与管理员分离；文档对哈希链的局限和「本机内容仍会发给模型」说得诚实；按白名单搬入上游的做法符合 D-2。
