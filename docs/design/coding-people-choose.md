# 让大家心甘情愿用 Muster 写代码

**状态**：计划，2026-11-22 拟定，等主人过目。Linear 免费额度已满（2026-11-22 建任务被拒），
任务暂时记在本文末尾的任务表里；额度解决后搬到 Linear 的 Muster 项目，挂在 CHA-272 旁边。

**是什么**：Muster 桌面端已经能在本机仓库里读、搜、改、跑命令（CHA-272 的前三块，见
[`../features/coding.md`](../features/coding.md)）。这份计划不追赶 t3、Codex 这类工具，
而是在 Muster 上按主人的口味慢慢定制，让技术和技术支持的同事**愿意**拿它来写代码、
查问题、修问题。

**参考**：主人最喜欢 Antigravity 的形式。它的回复总能说清楚做了什么、产出了什么、
改了哪些文件和代码、怎么验证的，让人一眼看出改得对不对。外界评价也最认它这点：
任务清单、实现计划、完成后的 Walkthrough、截图和录屏，人可以在上面评论，
agent 按评论修改。差评集中在早期不稳、额度紧、有时做的事看不懂。

## 为什么现在没人愿意用（判断）

1. **没在真实场景跑过**。`coding.md` 写明：桌面 app 里还没用真实模型完整跑过一次。
2. **看不清它改了什么**。收尾只要求“几行说说改了哪些文件”（`runs.ts` 的 `CODING`），
   每次形式不一样；文件名、命令、commit 都是普通文字，点不了。
3. **一次回复的改动散在右侧面板里**，没有“这次改了 N 个文件 +a −b，点开审”的入口。
4. **大改动直接开干**，不先给计划，人插不上话。
5. **UI 改动看不到结果**：没有模拟器，没有截图做证据。
6. **并行和交付缺环节**：没有每个对话独立的 worktree，不能一键提交和开 PR，没有真终端。

## 原则

- **证据优先**：每次回复都能核对，包括改了哪个文件、为什么改、跑了什么命令、结果如何、
  有没有截图。说不出证据的，就不算完成。
- **人始终插得上话**：计划、改动、截图都能评论，评论就是下一条指令。
- **先用起来，再加功能**：每一阶段都拿真实的小项目试，按试出来的问题排下一步。
- **不改现有的边界**：对话循环在服务器，动电脑的在桌面 app，一切过网关；
  只在用户要求时才 commit、push 或开 PR。

## 阶段与任务

### 阶段 0：拿小项目试（马上开始，贯穿全程）

- **试用记录**：在 3–5 个真实小项目上用桌面 app 从头做到尾。每次记下：
  任务、用了多久、哪里卡、哪里不信任、最后有没有保留改动。这份记录决定后面的优先级。

### 阶段 1：回复说清楚（Antigravity 式收尾）

- **固定收尾结构**：每次动过代码的回复，结尾固定四节：
  1. 做了什么
  2. 改动：按文件列，每个文件一句为什么改
  3. 验证：跑了什么命令、结果如何，附 commit、状态码、截图等证据
  4. 没做的，或需要你来做的

  harness 负责检查：形式不对就让 agent 补一次。CHA-268（完成后的回复不再堆过程中的话）
  和这条一起做。
- **回复里的标签**：行内代码、文件路径、commit、状态码渲染成小标签；文件带类型图标，
  点了在右侧打开该文件这次回复的 diff。复用今天做的文档 Markdown 渲染。
- **每次回复的改动条**：回复底部显示“N files changed +a −b ›”，配一个“Review”按钮，
  只看这次回复的 diff；“撤销这些改动”放在旁边。

### 阶段 2：人插得上话

- **先交计划再动手**：任务够大（多个文件、新功能）时，agent 先交一张计划卡：
  要改哪些、怎么改、怎么验证。人可以评论、批准或改范围；做的过程中任务清单实时打勾。
  小改动不走这一步。
- **在 diff 上评论**：在某个文件的某几行上写意见，发给 agent 作为下一条指令，
  并把这几行带上。

### 阶段 3：看得见结果

- **模拟器**：
  - agent 的工具：列出和启动 iOS 模拟器、安装并启动 app、截图（直接给模型看）、
    点击、滑动、输入、打开链接、读日志。用 `xcrun simctl`，Android 以后用 `adb`。
  - 右侧面板加“模拟器”页：画面实时显示，人可以直接点；可以框选一块加评论发给 agent。
  - harness 规则：改了 UI 的回复，必须附上模拟器截图才算完成；手机端界面对照既定的
    设计标准检查。
- **浏览器预览截图**：同样的做法用在网页上：agent 能截预览页，人能框选评论。

### 阶段 4：并行与交付

- **每个对话可选独立 worktree**：开对话时选“当前目录”还是“新 worktree”，
  互不干扰，做完可合回或丢弃。
- **提交和开 PR**：用户说了才做；提交说明和 PR 描述由 harness 根据它掌握的情况生成：
  改动、跑过的检查、截图。
- **真终端**：每个项目一个终端（PTY），人和 agent 共用，需要交互的命令也能跑。

### 阶段 5：让同事愿意用

- **一分钟上手**：挂一个仓库、自动读出它的检查命令、给一个示例任务、合适的默认模式。
- **技术支持的流程**：从一段日志、一张截图或一个工单开始，先复现，再定位、修复，
  最后附上证据。回复的固定结构同样适用。
- **看得见有没有用**：每个对话记下结果，比如改动保留还是撤销、检查是否通过、用户的
  一个赞或踩。每周汇总一次，用来判断大家是不是真的愿意用。

## 不做的

- 不接新的模型提供方（主人 2026-11-22：不是必要的）。
- 不去对标 t3 的多引擎、远程、手机控制。

## 怎么判断做成了

- 主人自己的小项目，能在 Muster 里从头做完，不需要切回别的工具。
- 每次回复都能在一分钟内看出改了什么、对不对。
- 同事试用一周后，愿意第二周继续用。
